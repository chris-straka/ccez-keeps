# Goal

Build `ccez-keeps-android`: a native Android app that works with the current frontend — same notes, same Cloudflare backend, same sync contract — so either client can be the daily driver and both converge. The web PWA (`ccez-keeps`, live at keeps.cstraka.dev) stays exactly as-is; this plan adds an Android client beside it, not a replacement of anything. Native apps were a non-goal of the web plan; this plan supersedes that for Android only.

## Success Criteria

- Same notes everywhere: create/edit/delete/search on Android, syncs with the server and the web client with last-write-wins and no duplicates.
- Fully usable offline: airplane-mode create/edit/search works; syncs on reconnect.
- Auth without a browser login: the app authenticates to the existing Access app on its own (service token), and no other device can reach the API.
- Web untouched: the PWA keeps passing its own gate (`bun install`, `bun run build`, `bun test`) with zero changes to its behavior; sharing happens through contracts, not source edits.
- Agent-only build: each work unit below is small enough for one agent to do and verify.

## Context And Current Facts

- Web backend is live and frozen: `GET /api/notes?since=<cursor>` → `{notes, cursor}`; `POST /api/notes/sync {upserts, tombstones, since?}` → `{applied, deltas, cursor}`; conflicts resolve by `updatedAt` LWW with JSON tiebreak; dissemination uses the server `seq` cursor. Full shapes in `ccez-keeps/contracts/api.md`.
- Pure sync logic lives in `ccez-keeps/shared/` (`note.ts`, `sync.ts`) with 51 passing bun tests; the Android port mirrors these files 1:1.
- Placement target `/Users/c/Swe/ccez-keeps-android` does not exist yet; this workspace root holds only the web project.
- Toolchain present: Java 25, `adb`, `sdkmanager`, existing `wrangler` OAuth session. No Android Studio — all builds headless via the Gradle wrapper.
- Target device is a physical Samsung over `adb`; no emulator dependency.
- Assumptions (reversible): minSdk 29+; distribution is sideloaded APK, no Play Store; UI language is Kotlin throughout.

## Constraints And Non-goals

- Android only. No iOS target in v1 (the `shared` module is structured so one can be added later).
- Web PWA behavior frozen: no changes to its routes, schema, or UX from this project.
- Single user, no sharing, no realtime collab — same as web.
- No attachments/media in v1 (text + color + pin/archive, mirroring web v1).
- Non-goals for v1: Play Store listing, home-screen widget (stretch phase), background periodic sync (foreground discipline matches web; see Key Decisions).

## Key Decisions

1. **Sibling directory `ccez-keeps-android`, not this repo.** Gradle and Bun toolchains, IDE indexing, signing configs, and CI do not mix well in one dir, and the web gate must stay runnable from a clean checkout without an Android SDK. Sharing happens through versioned contracts plus shared test vectors (Phase 2), not source coupling. Rejected monorepo: adjacency is not worth contaminating the proven web build.
2. **KMP `shared` module with pure logic only (android + jvm targets).** Mirrors `shared/note.ts` + `shared/sync.ts`: Note model, validation, `pickWinner`, `mergeNoteLists`, cursor rules — zero Android dependencies, tested with plain `kotlin.test` on the JVM. Kotlin Multiplatform exists to share exactly this kind of business logic across platforms while keeping native integration. Rejected putting storage/network in `shared`: it would drag platform drivers into the portable module for no v1 benefit.
3. **Native Android UI with Compose, not Compose Multiplatform web, and no WebView wrapper.** Compose is the modern native UI toolkit; a wrapper would just re-host the PWA (keeping its cold start and browser limits) while adding a second shell to maintain. The web PWA already covers the "same UI everywhere" option — the Android app earns its existence with startup speed, widgets later, and share-sheet later.
4. **Room for local storage, mirroring the Store interface.** Same tables semantics as the IndexedDB layer (notes by id, tombstones, cursor/push-mark meta), same view/search/sort rules. Room is Android's documented local-database layer.
5. **Ktor client for the API.** Multiplatform async HTTP client with plugin support including JSON serialization; keeps the door open if `shared` ever grows a networked target. Speaks the frozen `contracts/api.md` shapes byte-for-byte.
6. **Access via service token, not interactive login.** A service token (Client ID + Secret sent as `CF-Access-Client-Id` / `CF-Access-Client-Secret` headers) authenticates the app without a browser round-trip; the Access app gets a Service Auth rule for it alongside the existing owner-only browser policy. The secret lives in EncryptedSharedPreferences, never in source or logs.
7. **Parity by conformance vectors, not by code sharing with web.** New `contracts/vectors/*.json` fixtures in `ccez-keeps` (pick-winner cases, merge cases, validation cases) run by BOTH suites: a small bun test on the web side, `kotlin.test` on Android. Either implementation may evolve internally, but both must agree on every vector.
8. **Web does not consume the KMP module.** Compiling shared logic for the web UI risks bloating the 51KB-gzip bundle that the whole web project optimizes for, with zero user-visible gain. Conditional: re-verify only with a measured bundle impact if someone proposes it.

## Recommended Approach

Eight phases (0–7) in a sibling Gradle project (`shared` KMP module + `androidApp`), each phase verified before the next. The web repo gains exactly one thing: the `contracts/vectors/` fixtures plus a thin bun runner. Auth and backend stay as deployed; the only server-side change across this whole plan is adding one Service Auth rule (no Worker redeploy needed unless env changes, which it does not).

## Work Plan

### Phase 0 — Toolchain + scaffold (1 agent)

- Scaffold `ccez-keeps-android`: `settings.gradle.kts`, `shared` (KMP plugin, `android()` + `jvm()` targets), `androidApp` (Compose, Room, Ktor, Security-Crypto deps, no version claims beyond current-stable-at-build).
- Prerequisite gate: Gradle/JDK compatibility — Java 25 is present and may be too new for the Gradle line; pin a compatible JDK via Gradle toolchains (no reinstall of the user's JDK), verify `./gradlew :shared:jvmTest` runs green on an empty suite.
- Verify `adb devices` sees the Samsung; record the device id for later phases.
- Validation: clean `./gradlew assembleDebug` + empty test suites green.

### Phase 1 — `shared` pure logic port (1 agent)

- Port `Note`, `isNote`, `pickWinner`, `mergeNoteLists`, cursor/validation rules to Kotlin with identical semantics (including the JSON-tiebreak and intra-batch collapse).
- `kotlin.test` suite mirroring `tests/sync.test.ts` case-for-case.
- Validation: `:shared:jvmTest` green; a side-by-side diff review of each function against `ccez-keeps/shared/*.ts`.

### Phase 2 — Conformance vectors (1 agent, needs Phase 1)

- Add `contracts/vectors/` to `ccez-keeps`: `pick-winner.json` (`{id, a, b, winner: "a"|"b"|"error"}`), `merge.json` (`{id, lists, merged}`), `is-note.json` (`{id, value, valid}`), covering every existing edge (stale edits, tombstones both directions, ties, id mismatch, intra-batch duplicates, late-arriving old timestamps).
- Web: one bun test executing all vectors (must stay green — guards the frozen behavior).
- Android: one `kotlin.test` executing the same files via a sibling-relative path (`../ccez-keeps/contracts/vectors`, prerequisite: both checkouts side by side; CI note in README).
- Validation: both suites green on identical fixtures; any vector both sides dispute stops the line (contract question, not a code patch).

### Phase 3 — Android data layer (1 agent, needs Phase 1)

- Room schema mirroring the store: notes table (all Note fields + local seq-agnostic columns), meta table for pull cursor + push mark, tombstone write path, hard-drop path.
- `AndroidStore` implementing the same interface semantics as web `Store` (views, search, pinned-first sort, export/import JSON).
- Ktor client: `GET since=<cursor>` / `POST sync` with contract shapes, service-token headers injected from secure storage, response validation mirroring the worker's 400 rules client-side.
- Foreground `SyncEngine` mirror: debounced push-then-pull (~300ms), flush-until-quiescent, offline/error status, `deleteForever` (tombstone → flush → drop, throws offline).
- Validation: JVM tests with an in-memory Room database + fake HTTP engine covering the web `sync-engine.test.ts` cases (push shape, conflict convergence, late arrival, debounce, 401, delete-forever).

### Phase 4 — Android UI (1 agent, needs Phase 3)

- Compose screens mirroring the web shell: Notes/Archive/Trash, search, composer, editor dialog, pin/archive/delete/restore, dark theme parity, note-color tints, sync status line.
- App icon (reuse `ccez-keeps/web/icon.svg` source, adaptive-icon export).
- Validation: on-device smoke on the Samsung via `adb` (install, create/edit/delete/search across views, airplane-mode roundtrip); screenshot eyeball for theme parity.

### Phase 5 — Access wiring (1 agent, needs Phase 3; parallel with Phase 4)

- Create service token (dashboard or API); add Service Auth rule to the existing `ccez-keeps` Access app alongside `owner-only`.
- Verify-first: `curl` with the two headers against `/api/notes` and confirm the edge accepts AND the Worker's independent JWT check still passes (confirm `Cf-Access-JWT-Assertion` arrives on service-token auth before writing client code; fallback is a scoped decision, not a silent bypass).
- Store secret in EncryptedSharedPreferences via a first-run provisioning step (documented, manual, once per install).
- Validation: signed-out request denied; token request succeeds end-to-end sync; revoked-token request denied (rotate check).

### Phase 6 — Cross-client E2E + ship docs (1 agent, needs Phases 4+5)

- Two-client convergence: web PWA ↔ Android against production (offline-create on one, online edit on the other, stale-write loss, late-arrival visibility, no duplicates) — the same script shape as the web E2E, run once with Android as a party.
- README runbook in the Android repo: build (`./gradlew assembleDebug`), install (`adb install`), vectors prerequisite, token provisioning + rotation, rollback (uninstall/reinstall; server data untouched), signing note (debug key for personal sideload).
- Validation: E2E script green; web gate still green (untouched); install-from-APK on the Samsung works cold.

### Phase 7 — Widget stretch, optional (1 agent, needs Phase 6; shippable without it)

- Home-screen quick-capture widget (tap → blank note) only. Nothing else.
- Validation: on-device widget smoke. If it slips, v1 ships without it.

Dependencies: 0 before 1; 1 before 2+3; 3 before 4+5 (parallel); 4+5 before 6; 6 before 7. Maximum parallelism is 2 (Phases 4+5).

## Validation Plan

- `./gradlew :shared:jvmTest` + data-layer JVM tests green from clean checkout (after toolchain pin).
- Conformance vectors green on BOTH suites; a vector both sides dispute is a contract question, never a unilateral patch.
- On-device: install via `adb`, airplane-mode create/edit/search, reconnect sync, cross-client E2E green, Access denial checks (no token → denied; revoked token → denied).
- Web regression: `bun install`, `bun run build`, `bun test` still green in `ccez-keeps` (only additive vector files + one runner test).
- Highest-risk check: service-token request passing the Worker's independent JWT check (Phase 5 verify-first); second-highest: silent contract drift, guarded by vectors.

## Risks / Rollback

- Gradle vs Java 25 incompatibility: Phase 0 pins a compatible JDK via toolchains; never touches the user's JDK.
- `Cf-Access-JWT-Assertion` missing on service-token auth: verify-first with `curl` in Phase 5 before client code; no silent bypass as fallback.
- Web/Android drift: vectors + frozen `contracts/api.md`; any shape change needs a plan update in both repos.
- Token leak: secret only in EncryptedSharedPreferences + manual provisioning; rotation procedure in README; revocation is one dashboard/API call.
- Rollback is trivial: uninstall the APK; server data and the web app are untouched by every phase except the additive Service Auth rule (reversible in one call).
- Scope note: native apps were a web-plan non-goal; this plan does not reopen any web scope.
